## 〇、设计原话（作者，2026-10-05，逐字）

> 「我希望femogen和引擎是独立于宿主的。它和引擎的关系会更直接。也就是说，不管在哪个宿主打开它，它能实时反应引擎状态。如果引擎在跑，femgen这边就应该实时反应。现在它不是画布直连，他是绕了远路从dshAdapter接收信号。」

> 「毕竟现在引擎不能并行运行job，一次只能一个。那么不管哪个host的画布，反正只能运行唯一一个job嘛。我们未来引擎会支持多job同时运行，那时候画布应该可以支持分job查看。然后job和host挂钩，这样各host可能会有优先显示的选择性吧。但其实都是画布直连引擎。」

这段话与 2026-10-04 投影中心开始钮的拍板（「投影中心不归属于任何一个 Host，是所有 Host 的投影中心，做的超然一些」）是同一个哲学在画布上的重申：**面向引擎的观看面做超然态，宿主只是打开它的窗口之一**。本清单把画布照这个哲学改。

## 一、现状底盘——今天画布怎么连引擎（代码取证）

### 1.1 三种形态，三条路，没有一条是直连

| 形态 | 画布怎么打开 | 引擎状态从哪来 | 诊断 |
|---|---|---|---|
| dsh 插件模式 | 打进聊天窗构建，画布是聊天页里一棵常驻 React 子树 | 画布 → 宿主进程（同源路由族 + 一条宿主自办 SSE）→ 宿主进程 → 常驻引擎 | 两跳，宿主是必经的翻译官 |
| web 托管模式 | web 本地服务（缺省 8796）伺候 /canvas 页 | 画布 → web 服务（旧世界 /api 路由族）→ 常驻引擎；事件由服务转播 | 同样两跳，翻译官换了人 |
| zcode | 无。本地 HTTP 网关 2026-09-28 整体退役后无人伺候画布，构建产物在插件包里躺尸 | 无通路 | 画布在 zcode 已经死了 |
| vite 独立模式 | 手动开发服 | fetch 直连 localhost:8000——那个旧世界后端早已不在仓库 | 残骸。仓内唯一还活着的独立模式后端供给方是 web 服务自播自吃 |

### 1.2 dsh 两跳链路的精确形状（要拔掉的「绕远路」长什么样）

- 画布与宿主进程之间：同源 `/femo-plugin/*` 路由族（dsh 宿主注册，四十余条，运行、暂停、人类输入、会话状态、文件、对话框……）+ 一条宿主自办的 SSE（宿主进程里跑重放环，把引擎事件打上会话信封再广播给聊天页）。
- 宿主进程与引擎之间：公共层直连客户端（daemon-client）对引擎三个 HTTP 面（命令、SSE 直播、门铃心跳）。
- 画布在这条链上吃两类东西：**引擎原始事件**（宿主打上会话信封转一手）和**宿主自造帧**（运行态合成、变量世界归一、剧本变更通知等）。
- 代价：宿主养着一整面「画布专用翻译层」——事件信封、运行态合成、变量归一、按会话归属的状态镜像；换一个宿主就要照抄一遍；画布离了宿主就看不见引擎。

### 1.3 引擎对外面早已「浏览器就绪」——直连的地基是现成的

以下均为源码取证结论（关键指路见文末附录）：

1. 常驻引擎一张嘴挂四个面：命令、事件直播（SSE）、门铃、健康探针；投影中心 hub 与引擎同进程同端口，真实地址记在数据根的自发现件里。
2. **跨源头全开、零鉴权**：hub 的 HTTP 层对所有应答放跨源头，事件流应答同样带——任何网页（包括别的端口的宿主页面）都能直接发命令、直接订阅事件流。
3. **事件流对匿名者全收**：订阅参数「宿主身份」缺省时不启用归属闸、收全部事件（源码注释里有「未来收紧为必带」的预告——这是刀0 的由来）。断线重连带 Last-Event-ID 自动重放（环形缓冲 400 帧，追平帧信封顶层带追平标记），15 秒心跳。
4. **档案就是画布的渲染数据源**：按 job 号取档案返回全量——剧本原文快照、断点、变量世界、归属班底（哪个宿主哪个会话开的这场戏）；job 清单给全场元数据。两者都不要求调用方身份。宿主代码注释里本就写着「femoGen 凭 job_id 渲染/续跑的数据源」。
5. **控制命令齐全且无宿主门槛**：暂停（幂等）、续跑（剧本原文可从档案拿——投影中心的继续钮就是这么三步走的）、开新场（从挂载账本按路径读盘上现稿，班底按同名最近档案沿袭）。
6. 单 job 排他在引擎核心（开新场时引擎直接拒绝并报「已有另一场在跑」）——画布侧不需要任何互斥逻辑，引擎说了算。
7. 挂载共同账本的只读面已开：谁（哪家宿主哪个会话）挂了什么剧本、何时——「画布从挂载清单开跑」的料是齐的。
8. **流式字事实澄清（比对版补入，防虚功）**：逐字流事件（ai_token）只在引擎直连 LLM 的分支产生；dsh/web 的 AI 角色都由宿主执行体演，今天画布本来就没有流式字（宿主聊天流的逐字帧画布也一贯不消费）——直连在这件事上零损失、零增益。AI 发言的画布显示走 ai_done（引擎产，带全文）。

### 1.4 画布侧已有的伏笔（直连不是无中生有）

- **追平标记同位（比对版修正记）**：引擎 SSE 帧与宿主自办 SSE 帧的追平标记都在信封顶层（replay:true），画布判读追平帧的函数两种来路通吃。但信封并非全同形：引擎帧的类型字段叫 event（{type:'event', event:<名>, data}），宿主转播帧的类型字段直接叫事件名（{type:<名>, data}）——画布事件入口要**一处开壳**（把 event 对齐成 type），开壳之后整条处理链（调试窗摘要、节点匹配、人类等待、浮层）原样复用；「今天就能读懂、零改动」的原判不准确。
- **传输切换点现成**：画布只有一个形态开关 prop；独立模式还保留着一套完整的自带直连通道（后端已死、通道活着），说明「画布自带传输层」有活样板。
- **变量世界观测件天生分浏览器档**：公共层变量接口本来就有「浏览器信道档」（省流量、变量整包不上线），画布直吃引擎事件时的归一件是现成的。
- **投影中心网页是完整先例**：同源相对路径发命令、心跳看门狗按「问过没回」的欠账数判死、开始钮从挂载清单选剧本开跑——画布照抄这套纪律即可。

## 二、目标形态与架构裁决

### 2.1 总裁决：画布两张脸——引擎脸直连，宿主脸留宿主

**引擎脸（本次施工，直连常驻引擎）**：

- 事件直播：SSE 订阅，节点呼吸灯、断点亮点、人类等待全在这条流上（流式字现状事实见 §1.3 之8——dsh/web 宿主执行体模式下本就没有，直连不新增）；
- 状态校准：接通先问引擎（job 清单 + 档案快照），再让事件流往上叠；
- 停止与继续：直发引擎命令；
- 人类输入浮层的交卷：直发引擎人类输入命令；
- （远期）job 清单侧栏、分 job 查看、从挂载清单开跑。

**宿主脸（保留宿主回调，都是归属口诀判定的宿主私产）**：

- 会话剧本记录（record 唯一权威、剧本变更通知、乐观锁保存）；
- 开跑（运行按钮）：凭证注入、班底与会话绑定、清残留子代理、投影窗开窗——开跑是导演动作，牵动宿主物理形态，第一阶段仍由宿主代办（拍板点见 §四）；运行前的守卫询问（本会话剧本在没在跑）同属控制面，照旧问宿主；
- 文件面（导入导出、系统文件对话框、保存地址）；
- 干跑调试（宿主 subprocess 执行体）。

**裁决依据**（归属口诀：设想明天接入一个完全不同的 harness——不用变的就是 femo 系统的）：引擎状态、job 账、断点、暂停续跑，换任何宿主都是同一套——这是引擎脸，直连；文件对话框、会话记录、凭证，换个宿主就得换个写法——这是宿主脸，留宿主。

两条边界说清楚：

- 「宿主只准过引擎 HTTP 面」的纪律不破——画布直连走的正是那道 HTTP 面；而且画布本来就不是宿主，它是 femo 系统的自带工具，消费公共层与引擎面是本分，不算越权。
- 画布「纯显示者，不是指挥家」的本职不变——直连只是把「看戏的眼睛」从宿主手里拿回来自己长上，停止/继续两枚按钮直发引擎命令与今天「把宿主回调叫一声」同级，开跑仍走宿主（拍板点）。

### 2.2 「不管哪个宿主打开都看到同一场戏」怎么成立

单 job 时代：引擎全场唯一在跑的 job 就是答案。画布接通引擎脸后先问引擎（清单 + 健康探针），把在跑的场（或最近挂起的场）标出来：

- 跟随场的剧本与画布当前编辑图一致（本会话自己开的场的常态）→ 事件直接落在编辑图上，照今天的运行态显示（呼吸灯、断点、浮层全套）；
- 剧本不一致（别家开的场、或本会话画的不是这一版）→ 进「引擎此刻」观演面：顶部状态条常显 job 号 / 剧本名 / 班底 / 状态，主区用档案里的剧本原文走既有解析建图、直播点亮——**观演视图是画布内第二棵图，与编辑器内容彻底分离：编辑态（文本/图/脏标记/record）原封不动，退出即原样回来，观演绝不回写**（画布「不自动回写」红线在观演面的延伸）；观演态内编辑控件隐藏（纯显示），人类席只显「等待中」状态与提示、不亮输入框（画布是编辑器不是输入席）——看的是本会话自己的场且图即本场时，输入浮层照旧走宿主交卷，现状不变。
- 观演视图落地前的过渡期诚实不假装：剧本不一致的场事件匹配不上节点，照旧只进调试窗日志（喂食本就在节点匹配之前），状态条提示「引擎在跑 Job N（剧本 Y）」——比今天的一抹黑强，不假装能看。

已拍板的进出语义：观演面**自动进入**（不问）——引擎开跑且剧本不一致，画布当场切到该场的观演视图；**落幕画面定格**（终态留在观演视图里，不自动弹回编辑），用户一键回编辑；同一场重跑复用同一条观演视图。

**视图登记制（作者多 job 下拉未来的铺垫，本刀就按这个形状写）**：画布把「眼前这张图」抽象成**视图**，一张视图一个固定 id——编辑视图 id 恒为「编辑」（用户手头的画布图，唯一、永不被顶掉）；观演视图按场次起 id（如「job:2701」）。单场时代登记表里至多一条观演视图；将来多场并发，一场一条自动长出来、互不冲突（作者原话要义：「每个 job 都存在不同的下拉菜单里，互相不冲突」）。切换机制从第一天就只有一套（当前视图 id + 登记表），事件路由同理：引擎事件自带场次号，按「场次→视图」查表落图（现在表里只有一条，将来多条照查）——这就是「互不冲突」的机制本源。

多 job 时代（引擎改造完成后）：刀6 把状态条长成下拉菜单——置顶一条「正在编辑（未跑的稿）」（编辑视图本身就是清单第一项），下面按场次列观演条目。菜单所需的每项数据（job 号/剧本名/状态/班底）本刀起就在账上；视图切换、事件路由、跟随策略全是现成的——到时候是加法不是改造。

### 2.3 引擎地址从哪来（发现面裁决）

浏览器读不了盘上的自发现件，引擎地址必须有人喂，三条路按阶段用：

1. **宿主喂**（第一阶段）：dsh 宿主把自发现件里的真实引擎地址作为新 prop 传给画布（不许写死端口——公共层既有纪律）；web 服务伺候画布页时往页面里播种（它伺候自己的路由面时早就这么干，同一手法加一个键）。
2. **引擎自己伺候**（第二阶段完全体）：hub 把画布页也伺候起来（照投影中心页同款：现读磁盘、刷新即生效），画布页同源相对路径直连，零播种。顺带 zcode 的画布复活——开着引擎地址就有人伺候。
3. 画布连不上引擎时走既有「引擎启动中」芯片的重试回调，让宿主重新探一次地址再喂（引擎重生可能换端口）。
4. **远程可达性与透明转发后备（比对版补入）**：引擎 HTTP 面绑 127.0.0.1 是安全姿态，不翻案（无鉴权命令面绝不暴露给局域网）。本机浏览器（dsh 桌面窗、web 本机页）直连无碍；但手机走 tailscale 反代打开 web 画布时，浏览器够不着引擎——web 服务加一条**透明转发端点**兜底：逐字节转引擎事件流，不解帧、不加闸、不盖章，?since 原样透传（重放与 Last-Event-ID 续传随字节流自然工作）。可达性裁决：web 的地址端点按请求 Host 头判——回环打开的页面回直连地址，非回环回转发路径；画布逻辑不分家，讲的始终是引擎协议。dsh 恒直连（聊天窗在本机），不做此判断。

### 2.4 身份裁决：画布是引擎眼里一个合法的观察者格

- 画布订阅事件流时自报身份（femogen），引擎把这一格定为「观察者」：全场合法观看（等同今天不带宿主参数的全收待遇）。
- 为什么现在就定：引擎源码里有「事件订阅未来收紧为必带货」的预告注释——等收紧那天再做，全世界的画布一夜瞎掉；现在把观察者格立成合法身份，收紧就不伤画布。
- 画布要不要报门铃心跳？裁决：**不报**。门铃簿管「宿主在不在场」，画布开着不构成「这场戏该继续演」的理由；引擎闲时散场挂起在跑场是既有语义，画布看到的画面靠断线重连 + 档案快照自愈。

### 2.5 与引擎多 job 同跑改造的接缝对账（2026-10-05 两版对比后补）

另一份施工清单《compiler 多 job 同跑改造》管引擎侧：把「引擎同一时刻至多一场」改成「场次互斥 + 额度可调」——落库管道常驻化、场次号原子分配、JobManager 额度与场次占用账、SQLite 忙等保险。两份清单分工清楚、互不重叠：那份是引擎「能同时演 N 场」的能力，本清单是画布「不管谁开都能看、将来分场看」的眼睛。接缝上的对账结论：

1. **本清单刀0-5 与那份零依赖**：额度缺省 1 时「引擎全场唯一在跑的 job」语义逐值不变，画布第一阶段的所有假设照旧成立。刀6 的前置 = 那份的主刀落地 + 额度旋钮打开。
2. **过渡语义补丁（已吸收进刀2）**：额度已开、刀6 未动的窗口期，画布状态条与校准链不得假设「全场唯一」——按引擎清单的第一场在跑显示，并标注「多场进行中，分场查看待刀6」。
3. **发现的引擎侧缺口（建议那份清单吸收）**：引擎事件环的 checkpoint 帧原位替换**只按事件类型、不按场次分键**——额度大于 1 时两场并发各自存断点，后写的顶掉先写的，重放校准只能看见最后存档那场的断点。修法很小：替换键加上 job 号，每场各留最新一个。单场时代无感，多场时代必炸；落点在常驻进程的事件通道，不在那份清单列出的文件范围里——建议他们补记；若未吸收，并入本清单刀0 一起施工。
4. **次要备忘**：事件环 400 帧全场共享，多场并发下单场可重放的历史变短——画布校准以档案为准、事件只做增量，影响可忽略；事件重放不走归属闸（现行法：宿主直连客户端只吃直播不消费重放、画布观察者又是全收身份，都不受影响）——记一笔防后人踩。
5. **错误码无需画布适配**：满额沿用旧错误码、场次撞用新人话错误码，画布只当普通失败显示详情，零改动。
6. **第三摊挂账（两份清单都不含）**：投影中心/hub 的多场适配——「跟最新场」的跟随与视角计划的最新场兜底在多场并发时的语义（跟哪场、要不要选场），建议届时单独立项。

## 三、施工分刀

（每刀一个主题，改完即验；顺序即依赖。）

### 刀0（引擎一小步）：观察者身份

- 引擎事件通道：自报 femogen 身份的订阅放行为全场观察（与「缺省全收」同待遇），源码里「收紧为必带」的预告注释同步改口径（观察者身份合法，其余照紧）。
- 验证：沙盒带身份订阅，收到别家宿主开的场的事件；hub 全量自检全绿；常驻进程重启装载。

### 刀1（公共层一件）：浏览器版直连客户端

- 新件落公共层画布连接件目录（画布的数据通道是 femoGen 的东西、不是某宿主的——与既有画布 SSE 通道件同一哲学），从直连客户端抽浏览器可搬面：fetch 发命令、EventSource 订阅（引擎原生支持 Last-Event-ID 重连）、健康探针、job 清单与档案读取、跟随策略纯函数（pickJob：running 优先→最近挂起→idle；未来多 job 只换策略不换链路）。
- 发现与代拉（spawn 子进程、读盘）不搬也搬不了——那部分天生留在宿主。
- 验证：Node 单测（mock 网络 + pickJob 跟随策略）+ 对真引擎直测一遍命令与订阅。

### 刀1.5（引擎一小步，前置）：编译警告产信补一条

- 【比对版补入】事实：画布调试窗的编译警告今天来自 dsh 宿主合成广播（宿主从开跑/续跑回执取出再打给画布，run-control 两处）；驿站里的那份滞留件是给 main 的，不上事件流。画布改直连后宿主合成够不着画布，必须引擎补产信，否则画布对警告失聪。
- 改法：常驻引擎装配段产警告滞留件的同一拍，向事件通道多发一条 compile_warnings（帧带 job_id 与警告数组，形状照 dsh 合成帧）。纯增量：各宿主对未知事件落 default 记账无害；驿站滞留件照发（main 的知情渠道不变）。
- 随刀：dsh 两处合成广播退役（观察期）——daemon 事件成为唯一单源，否则过渡期 dsh 画布收双份。
- 验证：py_compile + 全量 pytest（跑前必设 FEMO_DATA_DIR）；引擎直测开一场带警告的剧本，事件流上见到该帧；dsh 画布警告单份。

### 刀2（画布核心）：引擎脸接通

- 画布新增引擎直连形态：新 prop 引擎地址（+宿主格名，供归属推导），有地址就开引擎脸。
- 事件直播改直连：订阅带观察者身份；**信封开壳一处**（引擎帧 event 字段对齐成画布的 type——见 §1.4 修正记）；追平帧不表演纪律照旧（标记同位同名，画布判读零改动）；过渡期宿主通道保留宿主自造帧（剧本变更等），引擎事件与宿主转播**二选一并轨，不许双吃**（防双份显示）。
- 状态校准链重写：接通先问引擎（清单 → pickJob → 档案）再叠事件流；校准材料=按钮态、断点亮点（档案断点标签）、等待旗标（waiting_human）、剧本指纹（供观演判定）、班底（未来优先显示用）；「本会话的场次」可从档案归属班底（宿主格：会话号）自行推导，宿主快照族 props 逐步退役。**时序照既有纪律：直连重放帧在建图/校准完成前入缓冲（画布既有恢复缓冲机制照用），校准完成后按序补放——宁可排队，不许撞空画布。**
- 停止/继续直连（暂停幂等；续跑三步走：档案取剧本原文 → 续跑命令——投影中心同款）；人类输入浮层直发引擎交卷。
- 变量世界画布侧直吃引擎三个工程事件（走变量接口浏览器档归一；裸 checkpoint 读 checkpoints 字段即断点高亮——与归一视图同名同形；func/assign 原生形状本就兼容）。逐字流帧继续丢弃（现状纪律不动）。
- 「引擎此刻」观演面：状态条 + 观演视图（档案建图 + 直播点亮，不回写编辑器）。**按 §2.2 视图登记制落**：视图 id 键控（「编辑」+「job:<场次号>」）、切换单一机制、事件按场次查路由——多 job 下拉的地基，菜单本身这刀不做。
- 过渡语义：引擎额度已开、但分场查看（刀6）未动的窗口期，状态条与校准链按「引擎清单的第一场在跑」显示并标注多场进行中——不假设全场唯一（见 §2.5）。
- 连接保活照投影页欠账判据（定期问健康探针、问过没回判死、硬拆立连）；断线重连**重走地址发现**（不信旧地址——引擎重生可能换端口）；浏览器 Last-Event-ID + 引擎重放环天然续传断线期间的帧，画布零额外工作（直连的白送红利，宿主转播时代没有）。
- **门0（动手前五分钟探针）**：在 dsh 聊天页真页控制台直 fetch 引擎健康探针——若宿主本体设了内容安全策略拦跨源，dsh 侧改走宿主 webServer 的同源直通代理（只转发不改写，不重新引入翻译层）。先探再动工。
- 验证：vite 夹具真页全链（mock 引擎 + 真引擎两档）、追平帧不表演回归、并行多线人类等待独立账本回归、观演视图与编辑器互不打扰、引擎代拉重生后画布自动重发现。

### 刀3（dsh 接线）：喂地址、瘦翻译层

## 五、红线与风险

- 画布三条既有红线在新通道下全部照旧并纳入回归：不自动回写（定稿必走显式按钮；观演视图是这条红线在观看面的延伸——编辑现场零触碰）、追平帧不表演、并行下人类等待记独立账本。
- 【比对版补入】「等人类」恢复面 v1 口径：引擎档案里等待人类只有旗标没有载荷；画布靠重放环里的等待帧（非常命帧，连接即补放）恢复等待面板；载荷被 400 环挤出的退化场景诚实显示（有旗标无面板），不为它加兜底——档案补载荷是引擎面小改，后续单独立判。
- 【比对版补入】流式字预期管理：dsh/web 宿主执行体模式下引擎不产逐字流事件，直连不新增也不减少（§1.3 之8）——施工与验收都不许把「流式字回来了」当目标。
- 归属闸收紧预告与观察者身份（刀0）必须在画布直连转正前落地，顺序不能反。
- 过渡期双通道必须二选一并轨，严防同一事件双份显示。
- dsh 聊天页内容安全策略是刀2 硬门（门0 探针先行）；被拦则走同源直通代理 fallback，直连语义不变。
- 改动边界：引擎侧只动常驻进程的事件通道（刀0）与装配段产信（刀1.5）、（远期）hub 静态面（刀5），不碰编译器执行体；投影系统与投影页零改动。
- 三份同步纪律照旧：改画布 → dsh 构建 + zcode 同步 + web 现读即生效；改引擎 → 常驻进程重启装载；动 Python 侧全量 pytest 必跑（跑前必设 FEMO_DATA_DIR）。
- 【比对版补入】「等人类」恢复面 v1 口径：引擎档案里等待人类只有旗标没有载荷；画布靠重放环里的等待帧（非常命帧，连接即补放）恢复等待面板；载荷被 400 环挤出的退化场景诚实显示（有旗标无面板），不为它加兑底——档案补载荷是引擎面小改，后续单独立判。
- 引擎死时画布（浏览器）无法代拉重生：显示断线状态，任何宿主客户端探活会顺手把引擎带回来，画布经重试回调重新拿地址——这是可接受的自愈路径，不做浏览器侧伪拉起。

## 六、补刀：画布改盯 runners + 直播线帧龄自愈（2026-10-08）

起因（用户报「femoGen 依然显示 2693 运行中，看不到当前的 2722」）：取证链三层咬合——①**引擎台账有 47 个 running，内存里真在跑的只有 1 个**（/engine/health runners=[2722]），2693 的场册文件自己就写着 running：2026-09-07 的 214 事故把「启动时扫全目录对账」退役后改「摸到才对账」，强杀重启的场没人摸就永远 running，历次强杀攒出僵尸堆；②画布跟随策略 pickJob 在台账里按 updated_at 挑 running，2693 是僵尸里最新的一个，画布照实显示引擎档案的谎；③2722 开演的 flow_start 活帧到不了画布——直播线 TCP 无声断开，onerror 永不来，而画布健康看门狗问的是旁路 HTTP 健康口，管道半死永远查不出。

用户拍板（逐字）：「应该收 runners，但应该都收，有多少收多少，也不是上限3。未来引擎会支持多开，那就应该所有runners全都收。画布盯着running不对，应该盯着runners」。

落法四件：

1. **引擎心跳翻案为 JS 可见的 ping 数据帧**（femo_daemon.py 一处）：旧心跳是 SSE 注释行 `: heartbeat`，浏览器 EventSource 的 JS 完全看不见（投影页手机断线同案的诊断）；改发 `data: {"type":"ping"}` 真实数据帧（15s 一拍、不带 id 行、不入重放环），画布帧龄判据的供给线。健康口加 `sse_ping: true` 开关键（老引擎无此键）。消费端全链核实零惊扰：unwrapEngineFrame 非 event 帧回 null；宿主直连客户端 daemon-client 只认 type==='event'；测试订阅器跳过非 data 行。

## 六点五、观演原位版——header 别变，只改画布内容（2026-10-08 用户拍板）

**起因（用户截图报「画布乱七八槽，两场叠在一起，header 也全乱」）**：旧观演覆盖层是 `absolute inset:0` 盖住整个 CENTER（工具栏+切换条+画布全被盖），自带一套观演头（ViewSwitcher/状态字/回到编辑钮）与编辑态 header 两套并存，背景透明让编辑画布透出来——观演态 = 两套 header 叠加 + 两场画布叠画。

**用户拍板（逐字）**：「正在运行的场次，显示也像正在编辑的场次一样，header区都按照编辑中的场次来，右上角那一系列运行停止控制按钮也都要在原位，上面也要使用横条上的下拉菜单来切换场次显示，总之就是header别变就好了，只改画布内容，且画布内容不要两场叠在一起。」

**落法（结构性互换，不靠遮挡）**：
1. **观演覆盖层退役**：桌面 CENTER 里那个 absolute 盖层整块删掉；观演内容改住画布格——Canvas 容器处三元渲染 `activeWatchView ? <观演画布容器><WatchView embedded/> : <编辑画布>`——同一格互斥渲染，编辑画布在观演时收起，叠画从结构上不可能。
2. **WatchView 新增 embedded 模式**（engineWatch.jsx）：不带自己的观演头（场号/状态/切换全部由宿主的横条交代）、外壳 absolute 铺满父容器；手机端 fixed/portal 老路不变（不传 embedded 照旧）。
3. **header 恒为编辑态那套**：工具栏（运行/停止/继续/打开/保存）不再随观演隐藏、原位常驻；观演时横条也常驻（与编辑态同位同皮，只换文案：绿点+「正在观看 Job N · 剧本名（状态：运行中 · 与编辑稿同版/不同版）」+ 同一个 ViewSwitcher 下拉），状态点颜色取当前观看场的实时镜像状态。
4. **按钮作用对象接观演场**：停止/继续在观演时作用于当前观看的场（activeViewRef 解析场号优先，否则回 pluginJobId/runId）——「header 别变」的另一半：按钮在原位，但服务于看到的场。
5. **事件路由补全**：帧喂给登记表里所有对上号的观演条目（旧法只喂跟随目标）——切换到任何一场，它的镜像都是新鲜的、零缺帧，不用等重连重放。

**验证**：vite 构建过（四轮迭代：原位容器 flex 铺满改 absolute 铺满——父容器非 flex 布局 flex:1 会塌高，实测前抓到改掉）+ watch-mirror 9/9 + engine-client 22/22 回归 + 仓库根构建过。手机端老路不受影响（提前 return 的独立渲染树）。金标准=用户刷新画布后切到运行中的场次：header 与编辑态完全一致（工具栏原位、横条下拉切换）、画布只显一场、停止/继续按钮直接作用于正在看的场，待用户。
