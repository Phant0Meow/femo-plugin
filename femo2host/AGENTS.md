## 一、门面与边界件

这个文件夹一半是引擎对外的唯一门面，一半是各宿主复用的公共件。

- 引擎门面（femo_api.py）：外面唯一准 import 的入口。
- 编辑器门面（femo_gen_api.jsx）：画布对宿主的唯一公开 API，与引擎门面同一取向。
- 引擎根解析器（femoRoot.mjs）：「引擎根在哪」的唯一答案——dsh、zcode 各持一份找根逻辑已收编于此。
- 常驻引擎（femo2host/python/femo_daemon.py）：引擎全家（含 hub、信柜管家、投递员）的常驻进程，每数据根一座、脱离宿主窗口，死了被任何客户端惰性代拉；对外三个 HTTP 面（/cmd 命令、/engine/events SSE、/engine/doorbell 门铃）。2026-09-27 两个桌面可见性/生命周期拍板落地：①**Win32 日志镜窗**（ctypes 纯标准库，任何 python 都能开——一版 AllocConsole 被 Win11 默认终端委派吞窗、二版 tkinter 被精简 python 卡死，皆实锤退役；窗=日志文件只读镜像，200ms 跟随；关窗=杀引擎、会自动重生）。可见性 2026-09-30 起归设置中心（_ConsoleGate：setting.json 愿望∩门铃在线，缺省隐藏，config_set 即时/0.5s 轮询实时显隐，ShowWindow 不碰 WM_CLOSE——杀车只归真人点 X；FEMO_DAEMON_CONSOLE=0 / --no-console / 终端手动跑永远静音，测试沙盒已在 conftest 与 zcode harness 静音）。②**闲时散场**（取代旧「闲时不散场」拍板）：点名门铃簿——四家宿主直连客户端每 10s 心跳（推送户带门牌、自取户空门牌，报到即算在线），簿子全空满宽限（缺省 1 分钟，FEMO_DAEMON_IDLE_GRACE_SEC 可调；2026-09-30 用户拍板由 5 分钟收紧——代拉重生是秒级事，宽限没必要陪长）→ 在跑的场诚实挂起（等 suspended 落盘确认，信柜断点留盘，续跑即收养）→ 引擎干净退场；running 但宿主全离线不陪死等。历史上的桥已随 2026-09-26 常驻化退役：生桥机器 bridge-launch/bridge-client 已「已退役-」改名静置（autoclaw 断供待其适配器重写，只余回滚路径），新代码勿再消费；femo_bridge.py 本体不改名——daemon 的装配模块住在里面，是活代码（main() 转发壳入口已随桥退役）。直连客户端（host/daemon-client.mjs）：宿主连常驻引擎的唯一公共件，见根 AGENTS.md 角色表。
- 设置中心（femo2host/python/setting.py，2026-09-30）：数据根 setting.json（FEMO_DATA_DIR 沙盒优先，否则 user_data/）的唯一读写口（读/校验/原子写/聚合纯函数）——引擎（/cmd/config_get、/cmd/config_set）是唯一权威，宿主不各读各的文件（两份逻辑必漂移）；现役键 console_window（各宿主对镜窗的愿望 show/hide，聚合=在线∩任一人 show，缺省隐藏），新设置在这里登记键与缺省。
- 驿站（mailbox.py）加投递员（mail_courier.py）：信柜和上门送急件的通道。投递两条腿：宿主支持直呼的就送货上门，不支持的信压柜等它自己来取。
- 投影中心（projection_hub.py）：单文件、纯标准库、零依赖；页面由它每次请求现读磁盘，改完刷新浏览器就生效，不用重启。同一个数据根只养一个 hub（2026-09-25 唯一化；2026-09-26 起与引擎同住 femo_daemon 进程）：客户端启动先探自发现件指向的 hub，活着就复用——喂送、花名册、信任账全走 HTTP；死了或还没有，代拉常驻引擎（hub 随之归位）。默认 127.0.0.1:8790，端口被占时向上顺延——宿主一律读自发现件拿真地址，不许写死端口。
- 投影中心网页（projectionCenter/ 文件夹，2026-09-26 自单文件拆分）：投影页本体，手机浏览器直接打开；hub 按白名单伺候（GET / 三个别名回页面壳，资产走 /pc/<名>，未命中 404）。主题 token 分层（换主题=theme.css 加一个 token 块），带就地输入席——人类输入也能从投影页直接交。共享可变状态只在 state.mjs 的账本 S 上；改任何一件，刷新浏览器即生效，不用重启。连接探活是页面显示层的分内之事（2026-10-03）：手机反代链路会无声死掉，页面自带心跳看门狗——定期向 hub 问 jobs 清单、按「问过没回」的欠账数判死、硬拆立连，hub 零改动（判据为什么不用「多久没听到帧」等实测教训见 main.mjs 头注）。
- 工具后端（femoToolcall/）：台账只读直查（chronica.py，两幕呈现）、干跑替身（femo_debugger.py）。
- 工作流教学正文（femoGenConnector/SKILL.common.md）：运行时喂给各宿主 AI 的唯一一份，各宿主展开后拼上自己的附录——正文只写所有宿主通用的教学与公用工具表，宿主特有的操作和工具归各家附录、正文不收；画布文件账本（femogen-files.mjs）与画布 SSE 通道（sse-core.mjs）也收在这个文件夹。

## 二、剧场比喻 → 公共层文件对照（femo2host/host/）

- 工具总纲（tools-core.mjs）——导演那套工具的名字、参数、校验、执行体全在这里定义，宿主只是注册调用。加工具只改这里，各家宿主自动获得。宿主不声明的能力不露出：附身工具（femo_possess）就是一例——宿主注入了会话身份、运行态、名册联动三件事才亮出来，不注入的老宿主零改动零回归。挂载态也住这里（createMountState + mount-registry.mjs 共同账本 `<数据根>/mounts.json`：谁（host+session）挂了什么、何时、会话显示名、地址或文字——撞键覆盖、文本挂载不复活、地址挂载重启恢复）——挂载是宿主侧导演工作台状态、不是引擎状态，账本只做记录、活真相在各家内存里。
- 电话机（已退役-bridge-client.mjs）——宿主和桥子进程之间那根管子的 NDJSON 协议机，2026-09-26 随生桥机器「已退役-」改名静置；sendActorFailure 已先迁 daemon-client.mjs。直连宿主一律用 daemon-client.mjs。
- 直连客户端（daemon-client.mjs）——宿主和常驻引擎之间那根管子的协议机：发现账双验、脱离母进程代拉、/cmd 命令（自动注入调用方身份）、SSE 直播（归属闸+live-only）、门铃心跳；stop 只断自己不发 shutdown（关窗戏演完）。
- 分诊台（event-core.mjs）——引擎每声播报的调度；单通道化之后只管记账、翻黑板、分拣。宿主接入面（2026-09-25）：账本可外置注入——多会话宿主把自家的运行态账本喂进来，镜像与各消费方同读一本；「事件归属哪个会话」「每类分拣行怎么显示」也都可以注入自家裁决；整类事件还可整体让渡（宿主自有语义全接管）。什么都不注入就是缺省行为，老宿主零改动。黑板（run-state-core.mjs）是「现在演到哪了」的快照。
- 演员核心（subagent-core.mjs）——一个 AI 角色演完一轮的全部簿记：料包怎么给、在飞怎么登记、占用怎么采样。
- 停靠经纪人（node-retry.mjs）——「重试还是放行」的裁决与租约；传话走驿站。
- 拼词员（notice-core.mjs）——戏停下来时给主模型的汇总措辞，全项目唯一一份，连终局广播的符号口径也归它。
- 交卷信封（speech-core.mjs）——人类和演员交卷的格式唯一出处；信封词汇按席位分：AI 与主模型带 output 栏、人类席带 chat_text 栏，寄错席位引擎响亮报错（细则见 femoCompiler 守则 §三）。
- 教条展开器（skill-expand.mjs）——宿主附录 {{INCLUDE}} 与 {FEMO_ROOT}/{HOST} 占位符的展开唯一一份（2026-09-29 收编：此前 zcode/dsh/autoclaw 各手写一份、已漂移），四家宿主同吃；模板与正文见 femoGenConnector（§一）。
- 幕布誊抄（projection-core.mjs）——去重、段闸门、视野分派（见 §四）。
- 慢重试（api-retry.mjs）——请求错误的五段退避，永久错误直通。
- 桥启动三件套（已退役-bridge-launch.mjs）——「宿主怎么把桥拉起来」的启动命令行组装、进程适配壳、惰性拉起加探活，2026-09-26 随生桥机器「已退役-」改名静置；ensureBridgeReady（就绪等待）已迁 daemon-client.mjs 在役。
- hub 地址解析（hub-client.mjs）——投影中心地址的唯一解析口：端口被占向上顺延时，宿主跟着自发现件走，不会把行静默喂进邻居 hub（真实事故）。
- hub 喂送协议机（hub-feed-core.mjs）——「宿主 → hub」上行的唯一一份：双路微批（job 路有戏才喂、会话路无戏照喂，各 40ms/20 条单飞）、段引用 ref（引擎令牌）/segRef（宿主自造键）语义互斥、宿主轮容器账（自开自收、幂等键从 seq 推）。best-effort 静默是纪律；要「诚实失败」的同步场景用它的裸 POST 面（postFeedFrames + outsideRowOp）。dsh 的 hub-feed.ts 只剩注入三件事（喂送地址/来源标签/会话寻址），zcode 网关的戏外行喂送吃同一份。
- 上门信分拣（mailbox-push-core.mjs）——投递员敲门送来一包信之后「该办哪件事」的唯一裁决；宿主只剩插座，按裁决执行本宿主的动词。
- 运行控制裁决（run-control-core.mjs）——「暂停一个 Job」的完整语义正身：给编号就按引擎档案裁决现态与归属，不再认宿主记忆里「最近一个 Job」——那样会停错戏。
- 端上共享规范件（hub-render-core.mjs）——投影页和 dsh 投影窗都要做的「呈现判断」唯一一份：哪些视角能亮人类输入席、场次行怎么称呼、工具结果归哪次调用。规矩是规范收公共层、画法留各端：页面由投影中心伺候这份文件引用，dsh 打包时直接捆进去。
- 选角账客户端（cast-core.mjs）——会话↔角色绑定的宿主侧唯一读写口，账本正身住投影中心（cast-preferences.json 提名账 + cast/<jobId>.json 每场选角账，裁决与形状见 projection_hub.py cast 段）：当选的角色由会话本尊出演（不再拉子代理）。提名制（2026-09-26 改判，废 09-25「唯一占用」）：偏好是票不是锁——查重的必要性边界是「一场戏之内一个角色一个演员」，不是「一个 soul 永久绑一个会话」；投递按 (job, soul) 查每场选角账、永不读提名账，多会话同好不产生投递歧义，所以唯一性只裁在开演定格那一次（同 soul 多票取最后指派；2026-09-28 再拍板：**定格以当前在线为准**——只在门铃簿活心跳宿主的提名里选举，不在线宿主上更新的同 soul 提名按没提过算，视图 scope='online' 与定格同吃一份判据 _cast_prefs_scoped，门铃钩子未注入退化为全账）+ 演出中冻结，戏散了无锁残留。账按宿主分格：绑在别家会话的角色，信寄对方那格留柜等它自取，发起方不代演也不报错（双宿主演出已走通）。与 hub 内部的剧本演员花名册（_cast）是两回事：那个记「戏里有哪些角色」，这本记「角色由哪个会话演」。导演的写入口在工具总纲的附身工具：提名写进这本账，附身判断（soul 核对/human 拒绝/演出中锁定）都在工具执行体里，不另开第二张账。
- 其余：干跑监工（debug-run-core.mjs）、交付队列（delivery-queue.mjs）、状态文件（state-files.mjs）、变量接口（variable-api.mjs）、会话登记簿（session-registry.mjs，无子代理化新增——钩子登记、possess 消费的跨进程账本：提交登记（谁刚按回车）供 possess 直达落提名，认领牌兜底；MCP 进程与钩子进程共用一个 JSON 文件）等，各文件头注释就是契约。
- Variable API 的由来：Function result / assign result 本想去 FemoGenConnector，转念觉得以后宿主侧插件也想展示程序结果，倒不如留成 API 形式放公共层——就叫 Variable API。

## 三、驿站（mailbox）——作者原话（逐字）

原文：docs/驿站设计.md，全文收编如下（原文件未动）：

我们理解mailbox就类似于驿站，已经送到家门口了。可以送货上门或者上门取件或者用户自己跑驿站。邮局/引擎相当于快递系统吧\~就是被寄走了或者收到了。

一个信件的定义维度：
0. 滞留件/急件
1. 收件/寄件
2. 驿站主动上门/客户主动跑驿站。
3. 请求远端/远端投递。
4. 上下文（带参数）、发言、通知。   （本来分戏内戏外其实是可以的，但我想那也太抽象了，人看不懂了也不好。还是全列出来吧。）
5. 客户Target host.  
6. 客户Soul ID。
7. 节点名（AI，人类，主模型都可以）


所以一个完整的zCode发言节点应该是：
收信、客户主动跑驿站、远端投递、该角色的上下文、zcode，soul id。
发信、客户主动跑驿站、远端投递、该角色发言、zcode，soul id。

有什么问题呢，请求远端会不会和要上下文搞混呢？除非是结合其他参数共同判断行为。比如：

戏内消息：
发信+远端投递+发言 = 节点发言。
收信+远端投递+上下文 = 节点上下文。
收信+请求远端+上下文 = 用户和主模型私下聊天、投影窗历史记录。
发信+请求远端+发言 = 目前没这个场景，未来万一会加人类强行节点外插话发言存Chronica……

戏外消息：
发信+远端投递+通知 = 什么报错需要操作？其实目前没这个场景
收信+远端投递+通知 = 结束/报错信息。
收信+请求远端+通知 = 如果有什么命令主动获取历史报错？目前没这个场景。
发信+请求远端+通知 = 用户主动给场外发点什么……目前没这个场景。


急件和滞留件。滞留件儿就是发过去之后，不急着投递给客户，压在驿站，直到下一个急件到来的时候，一起发给客户。这样是合理的。这样，我们就可以把 warning 抽象成滞留件，发给主模型，但是留在驿站。引擎发的结束信号是急件，急件到了之后，所有滞留件一起发。

驿站应该每条消息只对唯一 Soul ID 服务，上下文拼接由 Block Collector 负责。上下文带参数。

原话里的「几个维度」后来落成了系统的信封：一封信说清楚急不急、寄还是收、谁跑腿、谁发起、是上下文还是发言还是通知、送给哪个宿主、送给哪个灵魂、属于哪个节点。信有三种状态（在柜、送到、已拆）。系统化的全文见 ARCHITECTURE §4.5——那是原话的工程化，两边打架时回到上面原话。

**单通道纪律（现行法）**：派工只走驿站——轮到 AI 也好、轮到人类也好，事件流不再兜底派工，也没有「已办簿」；事件侧只管记账、翻黑板、分拣。节点重试、开演、人类插话、请求退避，全部改成信。作者原话：「**邮差扑空是修邮差的事情**」——投递失败修投递员（重投、死信），不给事件流加回退通道。以后凡是需要叫导演或演员的，常驻引擎直接产信进驿站，不走路由器。

**通道归属（急件 vs 滞留件）**：节点发给发言者的消息是**急件**；compiler 的终局/暂停通知是急件、发给 main；运行中来自 compiler 的警告（只要没停）是**滞留件**、发给 main——滞留件压站，等该收件人的下一条急件到来时一起发。（作者原话：「运行中来自 compiler 的警告是 held，发给 main。held 就是等着，等到下一条 urgent 为对应收件人的时候一起发。」）

**人类节点与 AI 节点同构**：两者本质相同——都是 compiler 把所需上下文发到 mailbox，再由宿主决定怎么处理；差异只在人类**不走 steer、直接显示**。

## 四、投影系统——作者原话（逐字）

#### 投影窗重设计 · 讨论稿

> 状态：设计原则已拍板，技术路径待细化。

**一、【角色运行窗】三种**

1. **子代理**——非主 agent 的其他所有 AI 角色。节点轮到他们说话的时候，他们会收到该他们看的上下文（由引擎发送），并进一步作出反应；一场剧本全程都由这一个子代理窗口来提供反应。但是用户无法查看，所以需要投影。
2. **主 agent**（导演兼主演）。节点轮到你说话的时候，引擎直接把你该看的上下文发给你，并收集你的整轮反应。不轮到你说话的时候，主窗口用户和你依然可以聊，不影响；引擎只是在轮到你的时候主动叫你。用户能看见（就是主会话），不用做投影。
3. **人类用户**——这个不等节点轮到，而是由引擎实时发送：每一处节点有 AI 实时说话的时候，如果这条消息的 scope 里有用户角色，就立即推给用户看见（最好能流式输出）。
   **如何实现推送是问题。** 用户必须能看见、能发消息，不用做投影（用户席本身就是交互面，不缺可见性）。

**二、【视角投影窗】三种（都是给用户看的）**

1. **AI 角色视角投影窗**。因为用户看不见子代理 session，所以需要专门给用户做投影。给用户看的依然遵循实时的推送：任何节点只要产生了新消息、只要这条消息的 scope包含这个 AI 角色，就立即显示在它的视角投影窗里。
2. **戏内视角窗**。FEMO 戏内所有消息，只要产生，都实时更新在这里。
3. **上帝视角窗**。FEMO 戏内所有消息 + 主窗口的消息（用户和导演的戏外闲聊）都在这里。

**三、技术路径**

1. **AI 回答**：引擎获取增量上下文，直接发给子代理；引擎获取增量上下文，直接发送给主代理。能够获取 AI 收到引擎之后反应的一整轮（可能包括多步工具调用），返回给引擎落库。
2. **给用户看**：节点输出时，按 scope 构建投影窗，最好能流式输出。要求是 showprompt、AI 名字、CoT、回答、工具、CoT……多轮一直到结束，这整块要输出在一起，**作为一整块；如果有多个节点在同时输出（par），不能穿插**。
用户要能输入（用户节点发言也走这条路线）。
3. 关于投影窗的事我想了想，投影窗分两部分，历史记录的部分可以从驿站拿。实时流式输出的部分得从host直接拿。

这场讨论后来落成三份工程文件：投影中心的行协议（docs/Specs/投影中心行协议.md，线上字节契约，第三方宿主十分钟接入）、投影合一设计（docs/投影合一设计.md）、公共层的幕布誊抄件（projection-core.mjs）。「一整块、不穿插」已做进组件结构；流式无缝交接截至 2026-09-23 的现状是「两批填」——逐字流仍走宿主本地打字机（模型调用在宿主，宿主在交卷那拍拿到全文）。「逐字流长进段里」的草稿层方案（宿主流帧带 wait_key → 段内草稿 → 交卷时替换）根因已查明，**2026-09-25 已拍板通过**（并发前提不变：写手不新增、转正单点归开容器的人），已随 dsh 事件面「最后一役」落地——打字流=宿主原生流帧转 draft-delta 喂进引擎开好的段；zcode 无逐字观测面（钩子只有边界事件），Stop 钩子收卷台词时同拍喂草稿（「提交即上墙」；宿主转写只装本回合最后一条消息，台词由收卷器自动收取）——两宿主收口权同归引擎出站（定稿吸收单点归开容器的人）。动投影之前先读《投影合一设计》讲演员回合段的那一节。

作者在定稿过程中的逐字拍板（各文档里都按引语保存）：

- 「Host 它是角色的字段之一」「不同的角色可能来自于不同的宿主」——来源标在角色身上，不是整场的属性；
- 「每个容器前面带一个前缀 dsh，毕竟一个容器里的信息肯定是来源于同一个宿主的……显示为细细的一条就好了」「把那个宿主信息放在时间戳和编号那一行，好像能更好看一点」——来源标一级一次，画在行头，不进内容；
- 「我希望你在网页上显示的方式，还是信实的、严格的体现 Hub 的数据结构」；
- 「只显示 Show Prompt，AI 的 Prompt 全程不用显示」——演出提示永远显示、人人可见，AI 的提示词全程不显示；显示规则收在投影中心的一个常量矩阵里，改显示只动它；
- 段键里的宿主前缀别删——多宿主共演同一场时引擎发的令牌必然撞号，不加前缀，两个演员的逐字流会交错着长。
- 「我希望它（hub）来规定槽位顺序，而其他宿主只是无脑照抄就好。每个槽位可以有个 tag。」

#### 投影系统的职责分工（现行法）

- **hostAdapter 负责**：递交流式输出内容、工具调用结果、各宿主自己的投影窗 UI、以及"去 hub 取信息"。工具结果的获取在 hostAdapter 侧，取到后传给 femo2host，**只走一条链路**。（作者原话：「要写递交流式输出内容、工具调用结果的功能，要写他们自己的投影窗 UI，以及要写投影窗去 hub 取信息。」）
- **hub（投影中心）负责整理**：哪个 session、哪个 job、哪几扇窗、每扇窗写什么、历史存哪。（原话：「而 hub 这里负责整理：哪个 session，哪个 job，哪几个窗，每个窗写什么，信息。」）
- **hub 数据结构优先**（2026-09-23）：（作者原话：「其实真正的问题不是html，而是数据，hub的数据。html只是用来反映数据的建立情况的。而hub的数据才是所有宿主公用的，所以hub数据如果建立的合理，各个宿主那边都会好弄很多。」）——改投影先想数据结构，页面只是数据的镜子。
- **窗两段式，接缝是行号**：每行的行号由 hub 分配，是全系统唯一的排序权威；宿主侧不存投影历史——冷唤醒读历史、实时走订阅，两段靠行号拼合无缝。宿主只有两个动作：上行「喂」整理好的行与直播帧，下行「画」订阅行协议渲染自家的窗。
- **hub 定槽位顺序，宿主照抄**：槽位顺序由 hub 规定，其他宿主只是无脑照抄；每个槽位带 tag（如 showprompt、名字），宿主靠识别 tag 来选（原话见上）。
- **前端忠实反映 hub 数据**：前端只忠实反映 hub 的数据，不自己造。（原话：「前端应该忠实的反映 hub 的数据。」）
- **段键用 wait_key，不用 node_name**：并行分支常跑同名节点（[看牌] 三分支、[投票] 四分支），拿节点名当段键必然串段——job 1810 踩过的坑。
- **行更新类广播的视角过滤走行本体**：控制帧顶层没有视野字段，拿帧去过滤会把戏内/角色视角全滤掉；要按行自带的视野过滤。
- **实时流结束时只清块、不转正**：正式段由引擎落账那一拍收，草稿转正必出双份。
- **段的两批填**：段在派工/等人类的信那一拍就建立（不是节点开始那拍），空段先出现（虚框加「正在…」），先填 showprompt 旁白，交卷那一拍再填思考/工具/台词收口；中间这段时间段不涨。

## 五、上移纪律

- 改壳不改面：把宿主里的实现上移到公共层时，原地留一个薄壳再导出，对外接口一字不变——所有既有使用方零改动，这是验收标准。搬之前先把硬编码路径的引用面查清。
- 把公共类再导出给 TypeScript 侧时，要用「继承一个空壳类」的方式；直接把类赋给常量会丢掉类型信息，类型检查立刻报错。
- 公共层和宿主的接缝全部是注入式回调，契约写在公共层文件头。
- 已上移公共层的清单（供对照）：草稿、"每个 dsh Session 对应哪些 Job ID"的记录、FemoGen Files（原 Femo files）、Femo Root、Variable API。（作者原话：「草稿放到公共层吧，别的 Host 也可以这样处理」「每个 dsh session 对应的都是哪些 job ID，这个记录也放到公共层」。）
