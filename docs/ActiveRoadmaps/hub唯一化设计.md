## 一、问题：hub 本该唯一，现在是复数

每个桥启动都自带一个 hub（进程内对象+HTTP 服务）。单实例时代天衣无缝；
3081+3083 双实例并行后暴露三层问题：

1. **地址簿抢写**：hub.json 是全系统唯一的地址权威，两个桥各自覆写
   （实测短时间 8791→8792→8791 变三次）。投影窗等读方按地址簿连到的
   可能是「不是喂行的那本」。
2. **内存账本分裂**：hub 的账本只在首次被请求时从盘上冷加载一次
   （`_load()` 仅在账本对象创建时跑），之后不重读。演出中的实时行只在
   喂行那本 hub 的内存里推（WS 订阅也在它那儿）——连错 hub 的投影窗
   停在旧快照/空白（job 2562 演出中 dsh 投影窗不显示的根因）。
3. **联机破功**：多宿主共演一场时，两台的桥各喂各的 hub——账本物理
   分裂，「多宿主联机」只剩信任集一半在 work。**联机的前提就是同一个
   hub**（数据根共享的拍板自然延伸）。

写侧（行带宿主标签、会话寻址、分格落账）没有任何问题——journal 每行
立即 flush，磁盘账实时完整共享。错的全是「hub 实例不唯一」这一层。

## 二、目标形态

**任意时刻全局只有一个活 hub**。桥启动时：ping hub.json 指向的 hub →
活着=**复用模式**（不自起、不覆写地址簿，全部交互走 HTTP）；死/无=
**自起模式**（现行行为）。复用的 hub 中途死亡 → 桥检测到喂送失败 →
**接管自起**（failover），回自起模式。

## 三、三根管子的改造

| 管子 | 现状（进程内） | 复用模式 |
|---|---|---|
| 喂行 | `hub.feed/set_cast/remember_display/set_owner` 直调 | `/feed` 端点已有（cast/display/owner 缺口→新增 `POST /hub-register` 三件合一，喂方登记语义不变） |
| 寄信 | `hub.set_mailbox(mailbox)` 进程内引用 | 人类席交卷→hub 写共享信柜（mailbox 是文件柜+target_host 分格 drain——双实例已实证并发可行）。实施前核 mailbox.post 多进程锁 |
| stdio 旁路 | `install_stdio_print_bypass(hub)` | 一期降级：复用模式下本桥 print 不进 hub 浮层（本地stderr 照旧）。可选二期补 `POST /prints` |

owner_resolver（hub 回调桥查 job 档案）在复用模式**不注入**——喂方登记
已覆盖（本桥喂行前先查自己引擎的档案、把 host_refs 信任集 HTTP 登记，
现行 `if not hub.has_owner(...)` 懒登记逻辑原样搬）。

人类等待镜像（projector.set_waiting_sink）：同喂行，HTTP 化（新端点或并
进 /hub-register）。

**⚠️ 寄信语义坑（实施中发现，必改）**：`hub.human_input` 寄人类信的
`target_host=self._mailbox_host or 等待态host`——**养桥 host 优先**。
复用模式下唯一 hub 是别人养的，`_mailbox_host`=养桥——3081 演出的人类
等待信会被寄进 3083 格，3083 的桥捞走投给自己宿主→「unknown job」丢弃
→3081 的戏卡死等人。**修法：优先级反转**——等待态自带的 host（等待镜像
是哪个宿主产生的，信就寄给谁）优先，`_mailbox_host` 降为等待态无 host
时的兜底（单实例下两者同值，行为零变化）。

**⚠️ failover 一期降级**：不做运行中热接管（热接管要重放全部接线——
mailbox 引用/等待 sink/花名册登记，复杂度高风险大）。一期：复用模式下
喂送连续失败→大声 stderr 留痕→**桥重启自愈**（重启时 ping 不到死 hub
→自然走自起）。唯一 hub 死亡窗口内实时行丢几条（内存的），磁盘账不丢
（每行即时 flush），投影窗冷唤醒自愈。

## 四、双模封装与 failover

桥内封一个 `HubClient`（local/remote 两态）：

- **remote（复用）**：全部喂送走 HTTP；连续 N 次连接拒绝（不是 4xx/5xx
  ——是连不上）→ 判定唯一 hub 已死 → 接管：`start_hub_server` 自起
  （端口从 hub.json 原端口起，被占再顺延）+覆写 hub.json+切 local。
- **local（自起）**：现行行为零变化。
- 判据纪律：只有「连接不上」触发接管；hub 返回的业务错误（400/500）
  不触发——那是喂的数据问题，修数据不换 hub。

## 五、风险与边界

- **桥是演出咽喉**：改造段正是 2026-09-19 NameError 被 except 吞掉、
  hub 静默不启动的事故区。施工时逐条对照该段现有「⚠️ 顺序纪律」注释；
  复用模式的全部失败必须「大声 stderr+回退自起」，绝不静默裸奔。
- **唯一 hub 死亡窗口**：养 hub 的桥先死 → 另一桥几秒后接管。窗口内
  实时行丢几条（内存里的），磁盘账不丢（每行即时 flush）——投影窗
  冷唤醒自愈。
- **网页/stdio 浮层**：print 浮层一期只有养 hub 的桥有；可接受（调试
  浮层是 dsh 单实例时代的诊断面）。
- **投影中心网页**：连唯一 hub，零改动。
- **zcode/autoclaw 宿主**：hub-client/cast-core 地址解析自动跟着
  hub.json 走，零改动。

## 六、验收

1. 单实例回归：单桥起=自起模式，行为与现状逐字节一致（含 8790 顺延）。
