## 一、引擎是什么：一个自圆满的剧场内核

引擎是埋头演戏的剧组：只管把戏演完，不抬头看观众，也不自己叫演员。这句话有三层设计含义，动引擎之前先吃透：

1. **自圆满**。femo 系统的三件套——job 管理、断点续跑、错误管理——全在引擎里，不依赖任何宿主。把引擎接到一个从没见过的 harness 上，这三样照常工作；把宿主全撤了，引擎自己也能编译、运行、记账（即「standalone」形态，宿主侧词汇用内置缺省）。判定一段逻辑归不归引擎，用全局总纲的口诀：设想明天换一个完全不同的 harness，它不用变的，就是引擎的。
2. **宿主侧的事实一律从清单来**。思考档位有哪些、默认用户是谁、宿主自称什么——这些是宿主环境的实事，引擎不写死：启动时应用一份宿主清单，清单缺失或个别字段缺失就回落内置缺省，standalone 照样自圆满。换 harness = 换一份清单文件，引擎零改动。清单里刻意不放模型目录——模型是动态的，由宿主在开演/检查时随协议参数注入，编译期校验模型白名单用的就是那份临时名单。
3. **不自己叫演员**。引擎从不直接去拽某个 AI：AI 节点把「料包」准备好、随事件交给宿主的执行体，然后守着专属频道等回信（详见 §七）。引擎认识的只有「执行体」这个抽象——宿主的子代理、网页席位、产品会话，在引擎眼里都是执行体。只有完全无宿主时引擎才启用自带的直连 LLM 出口，那是 standalone 的求生通道，不是主路径。

**引擎必须报错**（全局红线，在引擎里落得最重）：编译错、声明错、信封错位、快照版本不符、执行栈断裂……一律响亮报错，绝不静默兜底，绝不猜。这是个编译器，哪有好人家的编译器遇到错误会兜底猜一个运行的。变量名拼错、信封寄错席位这类事，静默过去的后果是戏演歪了还查不出为什么——比报错难查一个数量级。

引擎的表演流水线一句话：剧本进来先被标准化器誊工整、再解析校验成可执行的流程图；运行时把串行、分支、循环、并行、模块调用全跑起来；每个角色看过什么、说过什么，记在 SQLite 台账里，凭灵魂 id 跨剧本续记忆；每场演出一个独立的场次档案，随时暂停、断点续跑、断电重启后自动对账。

## 二、总纪律：能不动就不动

引擎逻辑复杂，经常压下葫芦浮起瓢，改了一处，另一处就坏了。工作方式要求：能不动 compiler 尽量别动 compiler！非改不可时，任何改动（包括顺手清理、纯排版级修改）都要先给出「为什么不会影响别处」的具体论证。

历史注脚（2026-09-22/23）：compiler 曾大改后整体回滚，最终保留的 diff 只有四行——human_wait 带上 showprompt。「能不动就不动」是用真金白银换来的教训。

**运行不符预期时，先分层定位，再决定动哪一层（作者定则）**。一次剧本运行报错、或效果不对，bug 可能藏在三个不同的层面，动手前先判断是哪一层：

1. **剧本层**（最常见）：剧本本身写错了，或者剧本设计得不好所以没实现想要的效果——改改剧本就好，**不应该动引擎**。
2. **引擎层**：剧本写的与语法文档一致，但引擎没有兑现语法文档的承诺——这是引擎的 bug，应该改引擎；**改之前必须告诉用户**（与 §十三「非动不可时先商量」同一条纪律）。
3. **语法层**：剧本与语法文档一致、引擎也没有 bug，但评估下来是这个点的语法设计得不好——不够普适，或者存在能更普适地支持各类场合的更好设计——这时考虑的是改语法；**语法设计提案必须与用户仔细商量**，不许擅改。

判断的标尺是语法文档：剧本写的一致与否，分开第一层和后两层；引擎兑现承诺与否，分开第二层和第三层。一般情况改剧本就够了——别一遇到报错就往引擎里扎。

**同一语义两份实现**（2026-09-28 实证）：引擎里主流程和分支各有一条走线，走线语义是两份复制的代码；join 的到达处理也是主流程、分支两个入口共用同一内核。改走线之前先回答一个问题：这条语义，主流程和分支各会不会走到？只改一条，另一条就带着旧语义继续跑——而且测试往往恰好锁着你想不到的那条，红着红着就把错处指出来了。

**注释是语义出处**。引擎的注释普遍带日期、拍板人、实锤案例号（job 号），是设计意图的第一手语境。改代码时先读注释、改完守注释——别把别人留的裁决依据当废话删了。反过来，注释和日志引用的旧行为描述都可能过期，动手前以当前源码为准逐行核对。

**观察期退役纪律**。确认无用的代码不直接删：整段注释、冠「已退役·观察期」、写明零调用的核查依据，静置数日无报错再整段删。引擎里大量这种段落——见到别误当活代码，也别热心帮忙「提前清理」，观察期未满。

## 三、编译期：先把剧本誊工整，再把关放行

编译分两步走。第一步是**标准化器**：把作者随手写的文本誊工整——语法糖、续行、裸动作引用、混在流程里的控制流，统一归一成无糖的整齐文本。设计意图是「作者可以写得随意，引擎负责先誊抄再理解」；但报错要指回用户原文的行号，誊抄会改写文本——所以灵魂校验在誊抄之前做，其余校验的行号定位也一律拿原始文本对照。

编译期校验的哲学是**能编译期拦的绝不留到运行期**，能一次列全的错误就一次列全（动作与作用域五大类校验就是把所有错误收集齐再一次拒绝，不让作者改一轮跑一轮），每条带行号、带原文、带改法。已经拦住的错误家族：角色灵魂不存在、声明模型不在宿主白名单、变量未声明（循环变量/迭代器/条件里的裸名）、引用未声明的动作或模块、函数节点缺「模块.函数」、入参缺映射、scope 引用不存在的角色、变量名撞保留字、声明了动作却解析出空流程图……这个家族只会变长不会变短：运行期炸过一次的错，考虑把它前移到编译期。

**报错（raise）与警告（warning）的分工**：raise = 编译拒绝，作者必须改；warning = 编译放行但作者应当知情，警告随编译回执上浮宿主。判断标准不是「严不严重」，而是「流程还能不能按设计跑」：join 落在流程环上必然无声卡死，但部分环形态仍可收敛——所以是警告；回到多出边节点会让分支数爆炸，但作者坚持要跑就让他跑——也是警告。新校验落笔前先想清楚自己进哪一桶。

**词法作用域（拍板）**：变量的可见域按模块的**书写嵌套**定（Python 式），与运行期调用栈无关。这条裁决是编译期与运行期能同守一部法的前提——编译期判断名字查不查得到、运行期解析名字走不走得通，用的是同一条查法，两边永远一致。它同时决定了：模块里可以引用祖先模块和全局的名字，兄弟模块的名字互相不可见。

**变量两维度正交（拍板）**：声明名带 `$` 表示 shared（全场一份，跨分支共享），不带则每 task 一份私有副本——这是「存几份」的维度；声明写在哪个模块的 vars 区，决定谁能看见它——这是「谁可见」的维度。两个维度互不约束，模块里声明 `$` 完全合法；同一可见域内同名声明（含 `$x` 与 `x` 规范名相同）直接报错。

**预定义变量**（2026-10-04 拍板）：`all` / `allAI` / `allHUMAN`——全部角色、全部 AI、全部人类。落法是解析收尾自动补三条脚本级声明，与作者自己在 vars 区写同名变量完全等价，作者显式声明优先。设计上刻意走「补声明」而不是「加特权」：名字进了声明表，之后一切变量位（赋值、插值、循环、条件、断点补种）零新路径自动生效——将来再加预定义名，照这个落法。

**两份语法检查是设计不是重复**（全局解耦铁律在语法检查上的落点）：引擎与 femoGen 画布各有一份语法检查、各自闭环——引擎不带画布要能编译，画布不带引擎要能出图。新加校验时对照前端的检查清单，两份各自补齐；规则正文一致，严度允许引擎侧更进一步（例如 `$` 引用要求该名字声明为 shared，引擎先拦，画布宽松但同样能抓未声明名）。

## 四、变量世界：声明说了算，分支各拿各的副本，汇合按规矩合并

- **声明表是唯一权威**。一切读写先查声明，未声明读写一律响亮报错——不猜、不现建、不默认空值。这条在变量世界格外较真：静默兜底的变量错误会沿着上下文传给下游每一个角色，戏演歪了没人知道歪在哪。
- **fork 的语义（宪法 1.1）**：一个 task 分叉，母 task 即终止（在变量世界层面不再存在），每个孩子拿一份**值副本**（深拷贝）。深拷贝失败（变量里存了文件句柄之类）响亮报错，绝不静默退化成共享引用——「分支串值」正是当年要根治的坑：两个分支改同一个对象，互相污染还查无实据。连带的设计要求写在报错文案里：变量中不该存不可拷贝的对象，要存就存它的描述（路径、id）。
- **join 的语义，与 fork 完全解耦（拍板）**：fork 只管分叉，后面有没有 join 与它无关；join 只管收拢——到达的 task 签到交出自己的环境，凑齐后合并出**新 task**，由最后到达的协程「变身」携带新世界从 join 出口继续，出口节点只跑一遍，其余到达者终止。等待集不认 fork 配对，按流程图拓扑反溯（沿 join 的入边反向收集上游分叉点与嵌套 join）——所以作者随便嵌套，fork 前不见 join、join 后不见 fork，编译期不做任何配对限制。
- **凑齐判定是 task 维度的「签到 ∪ 已终止」**：自然死亡的分支不用等（其对变量的修改丢弃、发 join_missed 警告）。这条判定防的是 join(all) 死等——作者的分支可能死路走尽，引擎不能陪葬。配合上一条：分叉点哪怕一个分支都没活下来，也算「已发生」，不会让下游 join 白等。
- **合并 = 三方合并，base 取血统最近公共祖先**。缺失哨兵与 None 严格分开（None 是合法变量值，缺了就是缺了）；字典逐键下钻（A 改了某角色的血量、B 改了另一个角色的血量，两个修改都保留），列表整值判定（位置语义不能按下钻乱合）。**冲突保留 base 值 + 完整留痕**——猫猫原话：「检测到 context variable conflict，编译器暂时默认保留base。未来会加处理conflict的机制。」留痕的结构就是为将来作者消费冲突的语法预备的，别删。循环变量的帧整帧豁免合并：循环变量各分支天然不同值，合了只会制造噪音。
- **join(N)**：凑够 N 个即放行出口，没到的活跃分支掐尾（只取消那一条链）+ 警告。循环体里的 join 每轮复用同一节点，靠代次区分新旧轮——上一轮的迟到者不许混进下一轮。
- **模块帧（宪法 1.2）**：模块 local 出模块即清。模块是词法概念不是 task 概念——进模块压帧、出模块弹帧清数据；嵌套调用沿书写链由内向外解析，兄弟互调可见，内外同名时更近的祖先胜出。
- **内建变量永远直通实时值**（当前是场次号与回合号两个）：读引擎现值，剧本写它报只读——消除「存进去的镜像与实时值分裂」的老病。将来再加内建名，照这个口径。
- **语言层的自律**（改变量子系统之前必知）：不发事件、不碰 IO、不反向 import 引擎上层；核心判定全部写成同步无等待——单事件循环里「检查+登记+唤醒」天然原子，规避先查后改的竞态。依赖方向单向无环：变量语言包 ← 接线适配层 ← 运行时。破坏这个方向的补丁一律不收。

## 五、演出进行时：一场戏怎么跑

- **协程模型**：单事件循环跑全部流程分支，阻塞的事（LLM 调用、落库、读终端输入）全丢线程池。快速节点（赋值之类）每步主动让出——不然并行分支会被饿死。LLM 调用按供应商限流（脚本 meta 可配延迟）。
- **六种执行者**：ai（问 AI 要台词）、human（等人类输入）、func（调剧本挂的外接 Python 函数）、assign（纯赋值）、mind（执行者是变量，每轮进节点时重新解析他是 AI 还是人，再整体走对应路径）、notice（公告：只把一句话按 scope 落进对话流）。mind 的存在理由：执行者是变量，编译期预判不了类型，那就别预判。notice 刻意做得极简：不检索记忆、不收集上下文、无回答者、无重试——它就是墙上的一张告示，编译期连「给它配了无效字段」都替作者把关。
- **回合号由引擎在锁内按「节点开工」顺序独立分配**，任何两行台账不可能撞键——这是并行分支丢台词事故的根治（旧法由说话人状态机推算，并发分支交叉推进必撞键，撞了还被静默去重）。取号后本节点所有行共用这个号。
- **收卷一拍（2026-09-27 拍板）**：发言的全部台账行（节点提示、舞台提示、逐轮转写）在**收卷那一刻**现取新号、单事务合写——要不全有要不全无。为什么不能开工时先落提示行：等待 AI 的几十秒里兄弟分支会推号，开工时占的号落库时已成旧号，会被增量窗口永久过滤（job 2613 实证的整条台词蒸发）。人类节点同理——等人类的几分钟里号照样在走。
- **台账行的可见性**：每行落库都带 scope（谁能看到这行）。scope 语义归引擎所有：不写=全员可见；self=只有发言者本人与 owner；列表=点名。台词行还按转写分离逐轮存（思考、工具命令、工具结果、台词各归各位），拼上下文时的可见性规则是：**自己的**思考与工具自己可见，**别人的**只可见台词——上游的思考不再泄漏进下游的上下文。将来引擎若扩展 scope 语义，必须同步宿主侧的主模型镜像清单（见协议文件里的同步注记）。
- **收幕语义（2026-09-28 拍板「分支没到 OUT 别收幕」）**：模块收幕只认「分支真跑到出口/跳出点」；死路走尽（无出边优雅停）完结**不算**收幕——本分支退出等待集，其余分支照常跑。为什么这么严：把「一个 AI 挂起退场」误判成「模块演完了」，会掐掉还活着的兄弟分支、主流程又重进模块、死路警告一秒一条无限刷（群聊室实锤）。配套两条：**分支报错即停**（掐掉兄弟再上报——错误不许被还活着的分支无限期捂住，否则等人类输入的分支永远收不了场，job 假装在跑、错误栏空空如也）；**分支挂起放行**（掐掉兄弟原样上抛，整场落挂起可续）。总原则一句话：**结束方式必须能被等待方看见**——真到出口、死路走尽、被掐、报错，各走各的路，不能全折叠成一个「完了」。
- **fork 收场后的账面复活**：模块内 fork 收场时母 task 已被记死，但模块走线在 fork 处收尾后母协程还要回主线继续——不把账面记活，此后所有断点都拍在「全员死亡、环境为空」的幽灵世界上，续跑秒跑完（当年四场存档同病灶）。主流程层的 fork 不复活——那里母走线是真的结束了，账面死亡是事实。
- **终点收场不等人**（2026-09-22 拍板）：戏到了终点直接收场，不等还卡在等待人类输入的分支——那种等待必须能被随时叫醒（等待线程随协程取消立即退场），否则收尾要拖好几分钟，终局消息全链迟到。

## 六、场次、Job 与断点：剧组的账本

先分清两套编号：**场次**是台账里的「书」（凭它续记忆、凭它算增量窗口），**Job** 是一次运行的档案（凭它暂停续跑）。一个 Job 挂靠一个场次，两套编号各数各的，互不借用。开新戏有活跃排他裁决：一场戏活跃期间不再开第二场，拒绝时带归属（哪个 Job、哪个宿主占着）；挂起的场各自留档，随时可续。排他是现状不是终点——**多场并行在计划中（见 §十五）**，从今天起写码就不要加深「全场只有一场」的假设。

- **Job 状态机唯一权威在引擎**。每个 Job 一份档案文件、原子写（临时文件+原地替换，断电瞬间要么旧档要么新档，绝无半截 JSON）；档案名就是编号——没有计数文件，文件在编号就在，断电不丢号。状态机：running → finished（戏演完）；running → suspended（挂起，原因三种：用户暂停、崩溃对账、节点暂停）；**一切运行期错误也落 suspended**（2026-10-01 拍板「一切 error 挂起可续」——挂起留断点，续不续、改不改稿重跑，都是用户的事）；failed 只属于构造期崩溃（连断点都没拍出来的场，重开等价于续）。终态化有幂等闸门，断点字段随之作废但文件保留。
- **断点模型：per-task 世界整包**。每进一个节点门口拍一次断点：每个存活 task 的变量环境、共享变量、分叉血统、task 活性、执行位置，整包快照。恢复 = 原样重建，不是字典逐键硬覆盖。恢复的执行模型是**分支直启**：不给根流程起协程（它多半早随分叉终止了），对快照里每个存活 task 各起一条分支协程、从各自记录的节点重放——该跑哪张流程图由模块栈顶决定；在模块内挂起的，恢复后跑完模块还要逐层弹栈回母流程续传。
- **续跑六关**：档案在不在 → 是不是还在跑 → 是不是终态 → 指纹对不对 → 挂靠的场次还在不在 → 有没有断点。设计意图是把「为什么不能续」一次说清：每关的错误码都是给人看的人话，每关的处置都是「拒绝并教怎么改」（重开一场），绝不猜、绝不半失忆续跑。有位置没变量的档案直接拒绝——位置在、变量丢的续跑比重开更危险。
- **指纹只对流程结构**（2026-09-06 拍板的宽松语义，翻正了旧口诀「改了剧本就是新戏」）：断点里只有「位置」强依赖流程图，变量世界是整包恢复的——所以台词、变量增删、布局注释的改动都不影响断点安放，照常续；流程节点和连线变了，断点位置在新图里才真的无处安放，才拒绝。**改了流程才是新戏。**变量增删另有容差：续跑恢复后，新剧本声明的变量按声明初值补种（警告说明：补种值是初值，不是断点时刻的中间态）；删掉的成为孤儿值，无人读即无害。
- **懒对账**（214 事故改造，别改回去）：引擎启动**不**扫全目录把「档案说在跑、本进程不认识」一律判死——档案是磁盘上多进程共享的资源，别的进程可能正活着，测试进程一启动就把生产的在跑场判死，这种事出过。现在只在「本宿主摸到某个 Job 的那一刻」裁决它，且三道闸门按序把关：本进程挂着执行体=它活着（哪怕循环僵死也轮不到对账判死）；非 running 的档案不碰；档案太新（一分钟内）不碰——可能正在装配途中。
- **上下文交付游标随断点落盘**（2026-09-28）：增量窗口的基线只活在内存，不随断点存档，进程一重启就回落到「自己最近一次发言」，恰好吞掉「收到节点提醒→说完落账」之间别人的台词。随断点存、续跑回填，游标只升不降（同进程续跑时现值可能比快照新）。

## 七、引擎怎么跟执行体说话

- **引擎不自己叫演员**。AI 节点开跑：引擎拼好料包（上下文、身份、提示词的原料，见 §九），随事件交给宿主执行体，然后守着专属频道等回信。宿主代跑模型、组装完整轨迹（思考、台词、工具调用与结果），按信封回传；引擎只取最终回复续流程，轨迹全文由引擎落台账。执行体最终失败（子代理死亡、超时）必须显式上报专用信号，不许伪装成空台词——引擎对「真的沉默」与「执行体死了」分桶处置，后者通知作者并把场挂起，续跑=换新执行体重演该节点。
- **料包的键词汇表归引擎，拼装归执行后端**。料包的键（安全须知/输出要求/角色卡/用户资料/场上对话/节点提示词/舞台提示词……）是引擎定义的词汇契约，单一权威在协议文件；每个键塞进系统层还是用户层、什么顺序、加什么垫话，归执行后端自定。宿主后端与直连桥各自拼装、无需逐字同步——共享的只有词汇表。引擎往料包加新键时，只扩词汇表、不改拼装。
- **交卷信封纪律**：执行体回传的台词必须装统一信封——AI 席带 output 栏，人类席带 chat_text 栏。两种信封寄错席位、或回传旧式的裸字符串，引擎一律响亮报错，绝不猜、绝不静默当成空台词放行——错位信封被静默读成空台词，比报错难查一个数量级。这是「引擎必须报错」红线在交卷口的落点。唯一的宽容例外：人类席空字符串 = 超时放行，设计内行为。
- **专属频道（wait_key）**：每个等待点（AI 的每一轮等待、人类的每次输入）一个唯一键，带世代前缀（场号）。旧一场的滞留信带着旧前缀，新一场的等待永远收不到——跨 Job 键不重合是机制性免疫，不靠人清理信箱。信箱本身另有保险：任何「就绪开跑」的时刻信箱必须从零开始。
- **停止纪律**：先取消全部协程、后唤醒全部等待者——这个顺序是红线（反过来存在同步推进窗口，协程可能拿着输入值继续跑赋值落库，僵尸推进）。取消必须走线程安全调度：从别的线程裸取消，取消令牌会被事件循环静默丢失，停止从此成了死信——「停止已受理、引擎永不收场」的事故本体。停止要幂等。终局措辞单份化：正常跑完才发「戏演完了」；被取消的戏只发「已挂起」——被取消的戏不许再报完成，谁在什么状态发什么话，不含糊。
- **人类输入的失败不算失败**：变量赋值违规 → 带错误反馈重新等输入（人重输=重试，引擎零新增机制）；反馈超限 → 清掉最后一次非法输入、按超时放行同款收尾——台账只留提示行留痕，非法文本不进对话流，防污染下游上下文。AI 沉默与人类沉默同款处理：放行，流程继续，不报错。

## 八、错误的四只桶

遇到错误先归桶，再按桶处理。四只桶的分界线是「**有没有东西被拒绝**」，不是「严不严重」：

- **FATAL**：跑不下去的——编译/语法错、模型配置错。发信号后把错误上抛，戏停（构造期=启动失败；运行期=挂起留断点）。
- **AGENT**：执行者的输出被拒了——赋值违规、格式错。本轮输出不落库、错误反馈给执行者、重跑该节点。这是唯一有「拒绝+重试」实质行为的桶。
- **WARNING**：值得作者知道、但什么都不拒绝——流程在无出边处自然收尾、迭代器不是列表空转、续跑补种变量……都是「能跑，但作者应当知情」。运行照常，提示上浮。
- **TOLERANT**：可忽略——连作者都不打扰。这是它与 WARNING 的分界线：WARNING 必须让作者知情。

**分工纪律**：错误分发器只负责拼报错信息、按桶发信号、给裁决；**重试循环留在运行时**，终止流程的执行权也在运行时——分发器不驱动重试、不终止戏。重试计数以专属频道为键（并行分支各数各的，不互抢额度）。

两条人味儿的裁决：

- **报错即通知作者，与重试并行**（不等重试用尽）：执行者看到报错后可能「聪明规避」——重试时干脆不写赋值语句，节点以正常收场而作者永远蒙在鼓里。所以每次报错作者都第一时间知道。
- **知情警告逐次如实报告，不去重**：同一警告反复出现，多半是流程真的在反复出问题——该修的是让流程反复走进来的原因，不是把重复捂掉；去重会让作者以为没事了（群聊室实锤：警告每秒一条的真因是收幕误判，修收幕后自然停）。警告文案要指明停的范围——停的若是分支，就别说「流程将停止」。
- **兜底必须知情**：引擎拿兜底值继续走，是设计内行为；但每兜一次必须同时告诉作者三件事——兜成了什么、后果是什么、怎么补。静默兜底等于把 bug 藏进运行时。作者明确设计过的形态（main 伪灵魂、无执行者的裸 AI）不警告。

两类重试，权责分明（作者原话：「第一种由 harness 负责……第二种 harness 已经把完整回答拿回来了，但 compiler 不满意，这时候不能运行到下一个节点，而是带着错误信息返回重试。」）：AI 的回答**没拿回来**（API 错）→ 归 harness，在请求层重试，引擎全程无感；回答**拿回来了但引擎不满意**（赋值违规、缺必赋值）→ 归引擎，带错误信息重跑该节点，绝不进下一节点。AI 的赋值只认节点 out 声明的白名单——预期外的赋值丢弃并警告（预期外信号可能是幻觉，不该进变量世界）；out 声明 required 的变量必须赋值成功，缺员走重试链。

**AI 演员失败有四层兜底，时钟刻意错位：内层还在重试，外层不许先判死**。从快到慢——请求层的快速重试（一分钟内）、插件的慢速退避（五段，合计约一刻钟）、停靠经纪人（十五分钟才判罚下场）、引擎的最终等待（一小时，超时按沉默放行）。动任何一层之前先对表——这是跨宿主与引擎的时钟表，单看引擎代码看不出全貌。永久性错误（没配模型、没额度、上下文超限这类重试也没用的）直接放行，不占兜底。

## 九、上下文投递：全量 vs 增量

一个 AI 演员每次上台前，引擎都要给它一份「你该看到的东西」当上下文。这份东西给多少，有两种给法。

**全量模式**：把这个演员**从开演到现在**、它有权看到的所有内容，一股脑全给。相当于每次上台都从头把剧本读一遍。好处是简单、绝不会漏；坏处是戏越长越啰嗦——它第三十次上台时，还要重读前二十九次看过的话，费 token 也拖慢节奏。

**增量模式**：只给**上次交付给它之后**新冒出来的内容。这正是作者的原话："只发乙的发言，仅此而已，因为前面的他都看过了。"

这里有个容易踩的坑要说明白：增量模式要靠一个「上次说到哪了」的锚点来切窗口。这个锚点叫**交付游标**——记的是「上次给这个演员拼料包那一刻，发到哪一行了」，**不是**「他自己上次发言」。为什么改：等一个演员说话的几十秒里，别人可能说了话、行也落了库——按「自己上次发言」切窗口，会把这些行永久跳过去（job 2613 实证）。2026-09-28 拍板：交付游标随断点落盘、续跑回填（见 §六）；游标缺键查库回落只留给「档案里也没有」的极端情形。首次上台的演员没有游标，窗口自然退回「从开场到现在」——这时候增量和全量是一回事，别以为选了增量就一定短。

**实际怎么选**：由接入它的宿主决定，剧本本身完全无感、不用管。机制上引擎只提供接口，请求方指定用哪种；走宿主执行体的宿主统一钉「首轮全量、之后增量」——第一次给全的（省得漏），后面每次只给新增的（省 token），这是最实用的默认；什么都不指定的调用方（引擎直连等）退回最保守的**纯全量**。这件事是拍过板的架构裁决（作者原话：「最好把功能放到 compiler 侧，让它提供 api，供 dsh 请求——请求全量就是本条之前所有，请求增量就是上次到现在新增。」）

还有个连带效果：全量模式下，连「你是谁、你的安全规则是什么」这类固定身份设定（角色卡、安全须知、输出要求、用户资料）都会随包重发；增量模式下这些就省了（首轮已经喂过）——身份层只进首包，跟着模式走。上下文本身是结构化的发言条目（谁的、逐轮轨迹），不是一坨排好版的文本——要全轨迹还是只要台词，消费方自己取。

**这段机制看哪里**：模式常量与路由、交付游标在 femoBridges 的上下文实现文件；料包按模式分集在引擎的块收集器；谁把模式钉进运行体，在门面 femo_api.py。

## 十、主模型下场（source:main）

剧本里写 `ai @主角 = source:main` 就是主模型下场。定稿语义如下（2026-08-31 定稿；此前的「fork 主会话」「宿主直调不拉子代理」等思路均已否掉）：

- **子代理是所有 AI 节点的基础设施**，source:main 也一样拉子代理。（作者原话：「source main也拉子代理，我们femo的所有ai节点的实现方式都是拉子代理，子代理是节点的实现方式，是节点的基础设施。」）
- **为什么拉子代理还是「本尊」**：只要用主模型同款基模、把主窗口完整上下文发过去，回答的就是主模型本人。（作者原话：「所谓主模型下场，就是带上了戏外发给主模型的所有上下文……全部的上下文，一个字一个标点符号都不少的全发给api，这才是主模型本尊。」）所以**不禁工具、不减上下文**——「不用禁手」。
- **上下文始终增量跟随**：只要剧本有主模型下场，任何时候往主窗口发消息（工具注入也好、用户插话也好），前面都带上截止当前、主模型视野可见的剧中内容；发过的部分打标记不再重发。可见性判定归引擎的 scope 语义，宿主镜像执行同一谓词——引擎扩 scope 必须同步镜像清单（协议文件注记）。
- **主窗口本身就是主模型视角的投影窗**，无需另设。（作者原话：「主窗口就是“主模型视角”窗口，他就是视角投影窗！所以我们并不需要另一个视角投影窗了。」）主模型下场的整轮（含思考、工具、流式）同时投影到上帝窗与戏内窗。
- **收尾前最后一轮注入**：剧本结束前，先给主模型补发最后一轮增量剧中内容，然后再发「剧本运行结束」。
- 直连模式（无宿主）不支持 source:main——主模型分身需要宿主代答，引擎响亮报错，不装。

## 十一、思考档位（thinking）

AI 演员有思考档位：剧本 actor 行可显式标注档位词汇，显式写 default 视同未写。档位词汇全集以**宿主清单**为准——引擎内置一份缺省（standalone 自圆满用），运行期以清单为准；非法档位编译期直接报错，不静默透传给模型网关。选档顺序为**「角色自带 > 子代理全局配置 > 部署默认」**，全链路（引擎、宿主、前端）已贯通。相关解析与校验在引擎侧，前端解析在 femoGen 侧——两侧都是各自语法检查闭环的一部分（两份闭环纪律见 §三）。

## 十二、门面与边界

- **宿主与引擎隔着一道墙**：宿主只准 import 门面（femo2host/femo_api.py，文件归属公共层但它是引擎对外的唯一脸面），不生 Python 子进程、不直接戳引擎内部——引擎内部随便重构，保住门面签名与语义就行，外面零改动。运行期宿主走常驻引擎的 HTTP 面发命令、听事件，见全局总纲。
- **编译产物是不透明句柄**：宿主拿到编译结果只许原样传回门面去构造运行体，禁止解引用——它的字段词汇不属于宿主契约。
- **运行体的装配也收在门面**：宿主不自己构造运行体、不注入私有属性——「信箱模式恒开」「宿主代跑 AI」「上下文模式」这些宿主协议假定的装配项，全是门面构造函数的显式参数。引擎内部改名不再波及宿主。
- **JobManager 每进程一个**，是排他裁决、档案落盘、僵死对账的唯一权威。运行体与 Job 的关系是「旁挂」：运行体不认识 Job，靠四条窄回调（开演、断点、状态变更、收场）把事实递出去，落盘归 Job 一侧——依赖倒置，运行体可以脱离 Job 单独跑（命令行裸跑就是证据）。
- **干跑是排练**：零 token 把剧本整个跑一遍，AI 和人类的台词都由替身代答，既抓剧本的 bug 也暴露引擎的 bug。干跑用独立 DB 沙盒，不写生产台账、不占 Job，可反复跑。干跑的正身是 CLI——干跑要能被随时终止不留僵尸、不与在跑的戏同进程，所以编程面退役、CLI 保留。
- **引擎不挂清单裸跑时自称「standalone」**：运行数据里见到它，多半是测试残留或忘了挂清单——先查环境，别去改名。
- **宿主接入时给引擎一份能力清单**（见 §一第 2 条）。

## 十三、写码规范（模块内纪律）

- **fail loud**：所有代码不许 try 静默兜底不报错，有错必须报错。每一处 try 都要能回答「为什么这里可以不炸」。
- **def 归属想清楚**：新逻辑进它语义上归属的文件，别往运行时主文件里堆。运行时主文件（FEMO_runtime.py）尤其不要动——非动不可时先跟用户商量（全局红线 §七 的模块强化版）。改运行体与 Job 的关系时，记住旁挂纪律：运行体不认识 Job。
- **解析打标、校验带行报错**：解析层遇到废除写法/可疑形态只打标，统一在校验段报错，报错带用户原文行号——两段式让报错文案集中、行号可靠。
- **单一事实源**：两处要用的拆解、正则、口径，收拢到一处共用；求值通道收敛到统一求值器。历史上「两处各自为政」出过点路径拆参失败、四套求值语义漂移的实锤。
- **依赖方向单向无环**：语言层（变量模型/求值器）零依赖——不发事件、不碰 IO、不 import 上层；接线适配层只向下 import；运行时在最上。判定新代码该放哪，看它需不需要发事件、碰 IO。
- **编译期校验一个都不能少**：历史上漏过「变量未声明检查」（作者原话：「后端有语法检查，但是漏写了变量未声明检查这个逻辑，咱们得补」）——新加功能时自查校验清单，别只做功能不做拦截。
- **报错文案是给作者看的**：写清错在哪、为什么错、怎么改；错误一次列全；文案里的建议要可执行（给出示例写法、列出可用名单）。
- **报错改不改看作者**：剧本和配套 Python 是自己写的，发现报错可直接改、不用问；是用户提供的，动手前先跟用户确认。

## 十四、测试

- 引擎与桥的测试都在 developer/tests/（pytest 从仓库根跑）：解析与校验（test_parser、test_var_decls、test_flow_ref_validation、test_compile_warnings、test_source_validate）、变量世界（test_v2_*、test_task_world、test_module_visibility）、流程事件与节点（test_flow_events、test_notice、test_mind、test_module_curtain、test_par_*、test_out_*）、Job 与断点（test_job_*、test_pause_*、test_v2_resume_e2e）、上下文（test_context_incremental）、信箱与桥（test_mailbox、test_mail_courier_retry、test_bridge_*、test_actor_failed）、错误四桶（test_error_buckets、test_error_dispatcher）。命名与内容大致对号，改哪块跑哪块，但**动引擎任何文件后全量 pytest 必跑**。
- **跑之前必设 FEMO_DATA_DIR**（沙盒三通道纪律，见根 AGENTS.md §八）——引擎的库、驿站、投影账本都要进沙盒，漏任何一条测试的信就会漏进生产。
- 干跑（femo_debugger）是剧本级自检：替身代答、独立 DB 沙盒、可复现种子；进阶 CLI（--module / --set / --assign-prob / --flaky）用法见文件头注释。跑出的问题先分清是剧本的错还是引擎的错——干跑抓的就是这两类。
- 验收铁律照全局：修 bug/写脚本后，「脚本自证/官方链验证通过」不算结论；真实演出目检上帝窗是金标准。

## 十五、已知边界与未来设计（留档，别当 bug 乱修）

- **多场并行是既定方向，尚未落地（2026-10-04 拍板留档）**：引擎现状同一时刻至多一场戏在跑（活跃排他见 §六），未来计划支持同时跑多场。**从现在起写码就要考虑这一点**：每场自己的状态跟着场走（run 级、Job 级作用域），不要为了省事挂成进程级全局——现在已有一些「本 run」粒度的内存态（错误重试计数、上下文交付游标、事件回调的绑定），它们天然各归各场，将来不用改；真正要提前想的是进程级共享物（台账库、JobManager 这些）在多场并发下的隔离与互扰。新代码拿不准时问一句：**两场戏同时跑，这段状态会不会串场？**答案是不会才许落笔。
- **并行分支里嵌套循环的解析图有一条已知断链**（分支直接签到汇合点，循环体一次不跑），已拍板以后单独修，留档在 docs/CompletedRoadmaps/。
- **模块调用点在母流程的循环体内时，断点直启恢复的栈序与真实栈序不一致**——恢复时会响亮报错、不会静默错跑；该组合场景的恢复待单独处理。
- **merge 冲突处理机制未来会加**（拍板 7，猫猫原话见 §四）——冲突留痕的结构就是为它预备的。
- **递归 module 的编译期拦截**未做（解析器头部有拍板留档）：当前靠运行期帧键撞键自然报错（同 task 递归进同模块会响亮失败），Parser 拦截落地后两边就都连上了。
- **join 落在流程环上**：编译放行 + 警告（部分环形态靠代次机制仍可收敛，作者知情后自行判断）——见 §三 报错与警告的分工。
